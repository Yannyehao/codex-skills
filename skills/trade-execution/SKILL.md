# Trade execution

This skill checks and records. It never clicks a broker's submit, cancel, or modify button, automates a broker, or creates an executable plan from chat. The human places every order. Chat is not the ledger: the local lifecycle service (`python -m zradar.trade_lifecycle`) is the single source of truth, and Notion is only a projection of it.

## Choose the mode first

- **Live execution / live position management**: use the service-backed workflow below. It requires an already-persisted, human-approved trade ticket and broker evidence; live mode never builds an executable plan from chat.
- **Historical execution replay**: only when the user explicitly asks to simulate or practise a past decision. Read [references/replay.md](references/replay.md) and use `scripts/replay_execution.py`. Do not read the lifecycle database, do not call any service `apply`, and do not reinterpret replay approval as live approval. Replay may construct a non-executable scenario from cutoff-safe evidence because every artifact is labelled `REPLAY`, carries `production_writes: false` and `broker_actions: false`, and cannot enter the live workflow.
- **Post-trade review of a recorded trade**: use the dedicated terminal-state mode below; it is neither replay nor live entry.

If the request mixes replay and a real order, stop and separate them. A replay never authorizes a broker action. A later live attempt starts over with `$market-review` on an explicit 固化, a service-persisted ticket, and a new human approval.

## Live setup and fail-closed loading

Read `config.local.json` beside this file (`config.example.json` shows the shape; real values stay local). Load the ticket only with the service's read-only `state` and `audit` commands, using the exact commands in [references/service-cli.md](references/service-cli.md). Feed their unedited output to `scripts/audit_ticket.py`. Stop and say exactly what is missing if the service is unavailable, the ticket is absent, or any approval-gate condition fails. Never reconstruct a ticket from chat, a screenshot, a review paragraph, or Notion, and never rename fields to fit an old export: a file that is not service output is rejected.

Read [references/ticket-contract.md](references/ticket-contract.md) for the raw fields, approval gate, and lifecycle. Read [references/capital-maturity.md](references/capital-maturity.md) for lane/quality/stage rules and scale-up. Read [references/stop-semantics.md](references/stop-semantics.md) before showing or attaching any protective order. Read [references/order-semantics.md](references/order-semantics.md) before showing any order form or recording any broker event, and [references/profiles.md](references/profiles.md) for the ticket's market (`US` or `A`).

## Workflow

1. **Load and audit (dry run).** Export `state` and `audit --ticket-id` to temporary files outside the repository, then run, with the Python this machine requires:

   ```powershell
   & <configured-python> -X utf8 scripts\audit_ticket.py pre-submit --state <state.json> --service-audit <audit.json> --session-date <YYYYMMDD> --bid <bid> --ask <ask> --quote-evidence <screenshot> [--prev-close <A-share>]
   ```

   Bid and ask come from the user's current broker screenshot, which is the execution authority. Any `BLOCKED` verdict stops the flow; state the cause and fix it with the user. The gate reads the approval straight from the service state: the persisted `approval` record (the `terms_sha256` stored with the human's `APPROVED` event, which must equal the ticket's `terms_sha256` and be flagged `matches_ticket_terms`) and the frozen parsed `profile` (lot size, T+N), whose hash must equal `profile_sha256`. Nobody types a hash: you never ask the user for one, and a missing or mismatched `approval` is a block, not something to supply. The gate also requires a named `human:` approver, a clean service audit, `A_CIRCLE`/quality `A` or `PRACTICE`/quality `VALID`, and the persisted budgets and floors. `AMBIGUOUS` and `REJECT` are never executable. Do not argue past a block, relabel a setup, or tweak a persisted number.
2. **Audit stop semantics.** `pre-submit` and `protective` both require a valid persisted `review.stop_semantics` (basis and activation) and BLOCK without it; read [references/stop-semantics.md](references/stop-semantics.md). Confirm the evidence supports the level and that the broker order can implement the activation. `basis.evidence` must carry the marker `canonical_trade_type=<TYPE>; policy=zge-stop-v1` exactly once, and the audit enforces that the type uniquely matches `basis.kind` and `activation`; a missing, mismatched, unknown or duplicate marker BLOCKS execution (terminal post-trade and historical review do not need it), and the audit never selects or changes a trade type. Only `BRICK_ZERO_DAY` is `INTRADAY_HARD`. If they are absent, ambiguous, unsupported, or the broker order cannot implement them, BLOCK and require a new draft and a new human approval; never improvise from chat. A `CLOSE_CONFIRM` or `NEXT_SESSION_FAILURE_TO_RECLAIM` stop is never shown or attached as a live intraday stop: `pre-submit` then prints only the human-only monitoring/exit procedure.
3. **Show the order.** Present the exact broker form fields, quantity (at most the approved), worst-case cost, max loss against `risk_budget`, reward/risk, the planned protective stop-limit (`trigger >= limit`, only for an `INTRADAY_HARD` activation; otherwise the ticket's human-only procedure), the market constraints, and every warning.
4. **Final human confirmation.** Ask the user to confirm the exact fields. Without a fresh, explicit yes, do nothing further.
5. **Record only on evidence.** After the user places an order, record it only from a screenshot or export showing it; record fills, partial fills, cancels, expiries, and rejections only from matching evidence. Build the args file per [references/service-cli.md](references/service-cli.md), derive the key with `audit_ticket.py idempotency-key`, validate with `audit_ticket.py check-args --op <op>`, then run `apply --op <op> --args-json <file>` once. Re-reading the same evidence never creates a second event. Record one transition at a time.
6. **After a fill.** Re-read `state`; repeat the stop-semantics audit; for an `INTRADAY_HARD` stop run `audit_ticket.py protective` with the stop fields the user is placing, and record `attach_stop` only after that run succeeds and only from evidence of the live order (`check-args` cannot see ticket state and never authorizes `attach_stop` by itself). For any other activation `protective` BLOCKS: give the human-only procedure and attach nothing. A cancel or expiry with no fill creates no position.
7. **Verify.** Read `state` and `audit` back and report the stored state, order status, open quantity, and audit result, not what you intended to write.

Allowed `apply` operations: `submit_order`, `attach_stop`, `amend_order`, `cancel_order`, `expire_order`, `reject_order`, `record_fill`, `record_exit_fill`, `expire_ticket`, and `cancel_ticket` on the human's explicit instruction. Never `approve`, `create_draft`, or `migrate`; `mark_reviewed` only through post-trade review mode below (it is not in `check-args`). Approval is the human's own act with the `terms_sha256` they reviewed, in the service; reading `state.approval` is evidence, never an approval input, and this skill never infers or performs it. Drafting is `$market-review` on an explicit 固化.

## Historical replay mode

Read [references/replay.md](references/replay.md) and keep the files outside production outputs. Build and obtain explicit human approval for a `REPLAY` scenario using only evidence whose `last_bar_date` is at or before `decision_cutoff`; this approval covers the simulation terms only. `source.decision_statement` records only the cutoff-time decision; a later case annotation may be cited by reference but its outcome must not be copied into PREPARED. Run `prepare`, then reveal exactly one `OPEN` event, then one `CLOSE` event. Version 1 stops at that close: it does not replay later sessions or manage a multi-day holding. Never combine stages in one input, point the open event at a full end-of-day bar, or summarize later prices before their stage is admitted. `--output` must be a new `.json` path and is never overwritten.

The replay helper loads `zge-stop-v1` from the sibling `market-review` skill, so one exact `canonical_trade_type` determines the stop. It blocks if the selector is absent. In particular, `B1_YELLOW_LINE_SWING` remains `CLOSE_CONFIRM`: an intraday move below yellow is not a stop; only the regular-session close decides. `BRICK_ZERO_DAY` alone uses `INTRADAY_HARD`, and a daily low can prove only that it triggered, never that a stop-limit filled.

Report every result as hypothetical with its evidence limitations. The helper verifies hashes, declared dates, stage order and stage-limited JSON; free text and images still require human hindsight review. The final journal may be passed to `trade-case-logger` as evidence, but this skill does not write the case, production ledger, lifecycle service, or broker. To place a real order, discard the replay path and return to live setup from a newly drafted and approved service ticket.

## Post-trade review mode

Only when the ticket's `state` is already terminal (`CLOSED`, `CANCELLED`, `EXPIRED`, or `REJECTED`) and the user explicitly asks to review it or write the review back. `mark_reviewed` is a human post-trade judgment, never an automatic step of execution and never a follow-on to a fill or exit. In this mode you may prepare and record `mark_reviewed` only from an outcome and note the user states explicitly: build the args file, run `audit_ticket.py post-trade-review --state <state.json> --service-audit <audit.json> --args-json <args file>` (it requires the exact terminal state, a human `reviewed_by`, a service outcome compatible with the state, a non-empty note, and a matching `ticket_id`; it prints `ARGS_OK` and never writes), then only on `ARGS_OK` run the lifecycle service `apply --op mark_reviewed --args-json <file>`, then read `state` back and report the stored state. Never infer the outcome or the teaching from fills, price history, or chat; never change thresholds or stop semantics; never rewrite the historical plan or ticket. With no explicit outcome and note, ask and write nothing. In any other state (including already `REVIEWED`) or for any request that is not about review, do not use `mark_reviewed`. Live broker actions stay human-only.

A pre-system historical import (state has `historical_import` and `pre_system_trade` true and a `historical_id`) never goes through that generic gate, which blocks it. When the user explicitly asks to review a `CLOSED` one and states the outcome and note, build the args file and run `audit_ticket.py historical-post-trade-review --state <state.json> --service-audit <audit.json> --args-json <args file>` (it requires both markers, current state `CLOSED` and not `REVIEWED`, a service audit scoped to exactly this trade (`historical_trades == 1`, `tickets == 0`, clean; an all-database audit is rejected), a matching `historical_id`, a human `reviewed_by`, one of `机会识别成功、执行完成` / `机会识别失败`, a non-empty note and key, and a UTC offset; it prints `ARGS_OK` and never writes). Only on `ARGS_OK` run the lifecycle service `apply --op mark_historical_reviewed --args-json <file>`, then read `state` back and report the stored state. The same no-inference and ask-and-write-nothing rules apply.

Creating or testing this skill authorizes no live write. A live `apply` needs the user's evidence for that exact fact.

## Scale-up

Only a proposal, from the service's same-strategy real-fill metrics and a policy the user supplies; never after one trade or on excitement. Run `scale-up` then `audit_ticket.py scale-up-proposal` (details in [references/capital-maturity.md](references/capital-maturity.md)). Present eligibility with metrics, change nothing, and send any larger size through a new draft and a new human approval.

## Stop conditions

Stop and ask when evidence is ambiguous (unreadable fill price, quantity mismatch, wrong symbol or account), when the broker's actual order differs from the ticket, when the service rejects a write, or when the user wants to change an approved field. A change within the approved bounds is an amendment recorded through the service on the human's explicit instruction; anything wider is a new ticket. Report a service rejection verbatim and do not retry it under a new key.
